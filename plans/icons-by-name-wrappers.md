# Icônes par nom : wrapper `@maz-ui/icons` dans une autre lib

Suite de [icons-by-name-standalone.md](./icons-by-name-standalone.md). Premier cas : `@accor/icons`, qui ré-exporte `@maz-ui/icons` sous ses propres noms (`AccorIcons()`, `AdsIconPrimitive`), avec ses SVG et sans les icônes de maz-ui. Plan côté Accor : `accor-core-library/packages/icons/plans/icon-named.md`.

## Problème

Ré-exporter ne suffit pas. Quatre choses sont figées sur maz-ui :

| Quoi | Aujourd'hui | Ce qui casse |
| --- | --- | --- |
| Le module augmenté par les types | `@maz-ui/icons` si le projet le résout, sinon `maz-ui` (`resolveIconTypesModule`) | Avec pnpm, une app qui n'installe que `@accor/icons` ne résout ni l'un ni l'autre : les noms ne sont pas typés |
| Le nom | le plugin `maz-ui:icons`, les logs `[maz-ui:icons]`, l'en-tête `Generated by MazUi() of @maz-ui/vite-plugin`, le fichier `src/maz-icons.d.ts` | L'app d'Accor affiche maz-ui partout |
| Le mode `lib` | seules les icônes de `@maz-ui/icons` restent des imports (`@maz-ui/icons/raw/MazX`) | Une lib qui utilise des noms d'Accor copie les SVG dans son dist, en double avec l'app |
| La CLI | `runCli` cherche le plugin `maz-ui:icons` et affiche ses messages | `accor-icons types` dirait "MazUiIcons() is not in the Vite config" |

Vérifié : augmenter `IconNames` par un module qui le ré-exporte (`declare module '@accor/icons' { interface IconNames {...} }`, avec `export type { IconNames } from '@maz-ui/icons'`) augmente bien l'interface de `@maz-ui/icons`. `MazIconPrimitiveName` et `IconString` voient donc les noms.

## Proposition (faite)

Des options facultatives, sans breaking change. Le wrapper les fixe, l'app ne les voit pas.

| Option | Effet | Par défaut |
| --- | --- | --- |
| `typesModule: '@accor/icons'` | Le module augmenté : `MazIconNames` pour `maz-ui`, sinon `IconNames` et `IconOptions` du module | `resolveIconTypesModule(root)` |
| `name: 'accor:icons'` | Le nom du plugin, le préfixe des logs, l'en-tête du fichier de types (`Generated by accor:icons`) | `maz-ui:icons` |
| `dir[].import: name => ...` | Le module du SVG d'un nom (sans son préfixe) : une chaîne (export par défaut) ou `{ from, name }`. L'app le bundle une fois avec les imports du module, le dist d'une lib garde l'import | aucun : le SVG est lu |
| `runCli(argv, logger, { command, plugin, pluginFunction })` | L'aide, le plugin cherché, les messages | `maz-ui-icons`, `maz-ui:icons`, `MazUiIcons()` |

- `@maz-ui/icons` passe par `import` en interne (`@maz-ui/icons/raw/MazX`) : plus de cas à part dans le `load`.
- `runCli` est exporté par `@maz-ui/icons/vite` : le bin du wrapper l'appelle.
- `generateIconTypes(names, { module, generator })` accepte n'importe quel module, pour le module Nuxt d'un wrapper.

## Hors périmètre

- **Deux instances du plugin** (`MazUi()` et `AccorIcons()` dans la même app) : les modules virtuels (`virtual:maz-icon/*`) entrent en conflit. Une seule instance, avec `defaultIcons` et les dossiers d'Accor. Documenter, détecter plus tard (un warning si deux plugins du même registre sont dans la config).
- **Renommer les modules virtuels et la clé du registre** : internes, partagés exprès (un seul registre, même avec maz-ui et Accor dans la même app).

## Tests

`src/vite/__tests__/wrapper.test.ts` : un wrapper `@acme/icons` en fixture. Sa commande écrit les types dans son module, TypeScript voit les noms par `@acme/icons` et par `@maz-ui/icons`, les messages et l'aide ont ses noms, l'app bundle le SVG une fois, le dist d'une lib garde l'import (export nommé ou par défaut).
